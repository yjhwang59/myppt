09 · Reliability

外部服務慢或失敗時，網站仍要可用

Static-first

Blog、案例與模板以 Markdown/MDX 內容為主。

DB fallback

課程查詢逾時時改用靜態 seeds，避免整頁失效。

Email 非同步

主要交易成功後寄信；寄送結果另行追蹤。

交易一致性

容量、重複報名與會員認領使用 transaction 或條件更新。

教學重點：fallback 是可預期的降級，不應被記成未處理的 Console Error；真正錯誤仍需結構化監控與告警。

11 · Security review

這份簡報能公開嗎？可以，但要分級

可公開

高階分層、一般路由分類、技術棧、匿名化流程、通用安全原則。

需模糊化

精確部署拓樸、內部 port、管理入口細節、資料表欄位與防護閾值。

不可公開

Secret、token、真實 DB host、Client ID、管理員帳號、內網 IP、備份位置。

安全不是靠隱藏架構；但公開內容不應替攻擊者完成資產盤點，也不可暴露可直接使用的憑證或內部定位資訊。

13 · Takeaways

三個帶得走的架構觀念

01

先完成任務

訪客先諮詢或報名，再低摩擦轉會員，兼顧轉換率與資料連續性。

02

UI 不是安全邊界

每個敏感 API 都要重新驗證身分、權限與紀錄所有權。

03

為失敗設計

資料庫、OAuth、Email 都可能暫時失敗；需要 fallback、稽核與可操作回饋。

下一步：將本簡報改寫為 Blog 時，進行一次「公開資訊紅隊檢查」，並建立公開版架構圖，不直接截取內部設定畫面。
